Research Proposal · EMNLP 2025/2026

SOLAR

Solver-in-the-Loop Constraint Acquisition and Refinement
Making LLMs reliably translate transit policy documents into formally correct, solver-verified scheduling constraints
01 — The Problem

What's broken today?

Transit agencies (MTA, MBTA, WMATA) hold hundreds of legally binding documents — union contracts, federal regulations, GTFS specs. Every rule in them must eventually become formal solver code to generate valid schedules.

"No driver shall operate more than 6 consecutive hours without a 30-minute break."
Plain English. But a scheduling solver needs this as precise mathematical constraints — and that translation today is done manually by expensive domain experts.
⚠ The Core Failure

LLMs are fluent at reading policy text but generate broken constraint code. They hallucinate plausible-sounding but mathematically infeasible rules. They blur "soft preferences" with "hard legal requirements". Worst of all — they have no feedback loop to even know when they failed.

02 — The Solution

What does SOLAR do?

SOLAR builds a closed-loop pipeline where the LLM generates constraint code, a real solver acts as automatic grader, and that verdict feeds back to make the LLM better. No human annotation at scale needed.

Policy Doc (NL) → Constraint IR (JSON) → CP-SAT Code → Solver Verdict → Train Signal ↺
03 — System Architecture

Full system design diagram

// SOLAR · End-to-End System Design
🧠
Stage 1
LLM Extractor — NL → Constraint IR
Fine-tuned Llama-3/Mistral reads policy text and outputs a structured JSON per rule: type (hard/soft), entities (driver, vehicle), thresholds (max 6h, min 30min), logic (conditionals, exceptions).
⚙️
Stage 2
Code Generator — IR → CP-SAT Python
Jinja2 templates fill in IR fields to generate runnable OR-Tools code. Edge cases fall back to an LLM prompt. All output wrapped in try/except before solver execution.
🔬
Stage 3
CP-SAT Solver — Execute & Verify
Runs generated code against a minimal synthetic schedule in a sandboxed subprocess (with timeout). Returns one of three verdicts:
✓ FEASIBLE ✗ INFEASIBLE ⚡ ERROR
🔄
Stage 4 · Core Innovation
CFFT — Contrastive Fine-Tuning on Solver Feedback
Solver verdicts become training data. FEASIBLE = positive example. INFEASIBLE/ERROR = negative pair. The model is fine-tuned to produce correct IRs — automatically, at scale, with no human labeling.
↻ Solver feedback loops back into LLM weights — each iteration improves constraint generation quality
04 — Agentic RL Connection

How RL fits into SOLAR

RL-Adjacent

SOLAR's CFFT loop has the skeleton of an RL system. The mapping is precise — and understanding it reveals both what SOLAR already is and where it can go next.

RL Concept SOLAR Equivalent Notes
Agent LLM Extractor + Code Generator The model that takes actions (generates IR / code)
Environment CP-SAT Solver + Scheduling Instance Stateless oracle that responds to every action
Action Generated Constraint IR or Code One constraint extracted = one action
Reward Signal FEASIBLE +1 / INFEASIBLE −1 / ERROR −0.5 Binary + partial; directly from solver, no human needed
Policy LLM weights (fine-tuned via CFFT) Updated after each batch of solver verdicts
Value Function Lightweight Verifier Model Predicts solver outcome before execution — acts as V(s)
Trajectory Single-step (v1) → Multi-step revision (v2) Current paper is 1-step; Agentic RL extension adds multi-step

Which RL algorithm fits best?

Three algorithms are relevant, at different stages of the project's maturity:

DPO
Direct Preference Optimization
Trains the LLM directly on (preferred IR, rejected IR) pairs without a separate reward model. Solver verdict determines which is preferred. Stable, simple, no PPO hypertuning.
CFFT as currently designed IS essentially DPO — solver replaces human preference labeler. Best fit for SOLAR v1. Lowest implementation complexity.
GRPO
Group Relative Policy Optimization
Sample N constraint IRs for the same policy sentence, score each with the solver, use relative rankings as reward. Same family as DeepSeek-R1. No separate critic model needed.
Best for SOLAR v1.5: when you have enough solver calls to rank multiple candidates. More data-efficient than PPO, more signal than DPO.
PPO
Proximal Policy Optimization
Classic actor-critic RL. Full reward model (the verifier) scores outputs. KL penalty keeps LLM from diverging. Proven in RLHF (InstructGPT). Most expressive but most complex to tune.
Best for SOLAR v2 (Agentic): when multi-step constraint revision trajectories are added and cumulative reward is needed across a document.
PRM + REINFORCE
Process Reward Model
Instead of rewarding only the final schedule validity, reward each intermediate step — each constraint extraction, each IR field. Finer-grained learning signal.
Longer-term research direction: step-level rewards for constraint type classification, threshold extraction, and logic parsing independently.

SOLAR v1 — This Paper
DPO / CFFT (Single-Step)
  • One constraint = one action
  • Solver verdict = binary reward
  • Contrastive pairs = DPO training
  • Verifier = lightweight V(s) proxy
  • No trajectory, no exploration
SOLAR v2 — Future Work
GRPO / PPO (Agentic, Multi-Step)
  • Multi-step revision over full document
  • Solver = callable tool (MCP-style)
  • Cumulative reward across trajectory
  • PRM for step-level constraint rewards
  • True Agentic RL — same family as R1
05 — What's Novel

Why hasn't this been done before?

Solver as Automatic Teacher

Prior work requires expensive human annotations. SOLAR uses the solver as a ground-truth oracle — scalable, free, and verifiably correct.

Real-World Regulatory Text

Other systems use clean toy problem descriptions. SOLAR targets messy, legally-binding policy docs where hard/soft constraint boundaries are implicit.

Hard vs. Soft Classification

No prior NLP work explicitly trains a dedicated objective to distinguish hard legal rules from soft scheduling preferences.

TransitOpsBench

First public NLP benchmark of FTA regulations, union CBAs, and GTFS specs. Cross-document domain shift evaluation included.

⚡ TL;DR — The One-Paragraph Version

  • Transit agencies have legally binding rules in English that must become formal solver code to generate valid schedules.
  • LLMs generate plausible-but-broken constraint code and have no feedback loop to know they failed.
  • SOLAR inserts Google OR-Tools into the training loop: generate → verify → use solver verdict as reward signal.
  • The CFFT training objective is essentially DPO where the solver replaces human preference labelers — automated, scalable, verifiable.
  • The natural v2 extension replaces CFFT with GRPO/PPO for multi-step agentic constraint revision — same architecture as DeepSeek-R1, grounded in transit operations.
