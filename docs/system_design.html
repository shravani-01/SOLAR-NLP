C Scripts That Need to Be Built

These are required by the research proposal but have no corresponding script in the codebase.

1. Multi-Domain Data Scraper

00_scrape_documents.py

The proposal specifies TransitOpsBench with 4 data sources: FTA regulatory docs, multiple transit CBAs (MTA, MBTA, WMATA), GTFS/GTFS-RT specs, and GPT-4 synthetic augmentations. Currently only one CBA contract is processed.

Proposal: "First public NLP benchmark of FTA regulations, union CBAs, and GTFS specs. Cross-document domain shift evaluation included."

2. GTFS Constraint Extractor

00b_parse_gtfs_spec.py

GTFS/GTFS-RT specifications contain formal constraint definitions (field validation rules, required frequencies, timing constraints). These need a specialized parser — different from CBA/FTA natural language patterns.

Proposal data source: "GTFS / GTFS-RT Specs" — structured spec format needs dedicated parsing logic

3. Synthetic Augmentation Pipeline

03b_synthetic_augment.py

Generate synthetic constraint sentences via GPT-4 to augment the training set. Paraphrase existing constraints, create edge cases, generate cross-domain variants. The proposal lists this as a key data source for TransitOpsBench.

Proposal: "GPT-4 Synthetic Augment." listed as TransitOpsBench data source

4. Cross-Domain Split Builder

06b_cross_domain_splits.py

Create held-out domain-shift evaluation splits: train on CBA, test on FTA; train on FTA, test on GTFS. The proposal specifically mentions "Cross-document domain shift evaluation." Currently splits are random, not domain-aware.

Proposal novelty: "Cross-document domain shift evaluation included" in TransitOpsBench

5. DPO Training Script

12c_dpo_finetune.py

The proposal states "CFFT as currently designed IS essentially DPO — solver replaces human preference labeler." But 12b_cfft_finetune.py uses standard SFT loss, not DPO loss (which needs chosen/rejected pairs formatted differently). Need trl.DPOTrainer.

Proposal: "The CFFT training objective is essentially DPO" — actual implementation uses SFT

6. Verifier Model

14_train_verifier.py

The proposal architecture includes a "Lightweight Predictor" that predicts solver outcome (FEASIBLE/INFEASIBLE/ERROR) before execution. This acts as V(s) in the RL framework and as an inference-time filter. No such model exists in the codebase.

Proposal: "Verifier Model — Predicts solver outcome pre-execution — acts as V(s)"

7. Jinja2 Template Engine

09b_jinja_templates.py

The proposal specifies "Jinja2 templates" for code generation. Current 09_generate_cpsat.py uses Python f-string templates. Need proper Jinja2 template files for numeric, boolean, soft, and conditional constraint types.

Proposal Stage 2: "Jinja2 templates fill in IR fields" — currently uses f-string templates

8. TransitOpsBench Packager

15_package_benchmark.py

Package TransitOpsBench as a shareable, versioned benchmark: standardized format, splits, evaluation script, data cards, license metadata. The proposal claims this as a novel contribution: "First public NLP benchmark."

Proposal novelty: "TransitOpsBench — First public NLP benchmark of FTA, CBAs, GTFS"
D Dataset Curation Process — Multi-Domain Coverage

The proposal requires TransitOpsBench: a multi-source benchmark spanning 4 document domains. Here's the current state and what needs to happen for each.

Transit CBAs (Collective Bargaining Agreements)

Union labor contracts from transit agencies. Dense with operational constraints: shift limits, overtime rules, break requirements, seniority rules, bidding procedures. Currently the only domain with a working pipeline.

Sources: MTA (NYC), MBTA (Boston), WMATA (DC), SEPTA (Philly), CTA (Chicago), LA Metro

Format: PDF contracts, 50-300 pages each

Scraping: Agency websites, FOIA requests, union archives. Most are publicly available PDFs.

Partially built
Scripts: 01 → 01b → 02/03 → 04 → 05 (one contract only)
Gap: Need to process 5+ CBAs for cross-document evaluation

FTA Regulatory Documents

Federal Transit Administration regulations. Contains compliance constraints: safety requirements, drug testing rules, ADA requirements, hours-of-service rules, maintenance intervals. Higher formality than CBAs.

Sources: 49 CFR Parts 600-699, FTA Circulars (C 9030.1E, C 4702.1B), National Transit Database reporting rules

Format: PDF regulations, HTML on ecfr.gov, structured subsections

Scraping: ecfr.gov API, FTA.dot.gov document library. Publicly available.

Not started
Needed: 00_scrape_documents.py (FTA module)
Gap: Different structure than CBAs — numbered subsections, cross-references, definitions sections. Regex patterns from 01 won't work as-is.

GTFS / GTFS-RT Specifications

General Transit Feed Specification. Contains field validation constraints (required fields, allowed values, timing constraints), frequency rules, and data format requirements. Semi-structured, more formal than NL.

Sources: GTFS Static spec (gtfs.org), GTFS-RT spec, GTFS-Flex, GTFS-Fares v2

Format: Markdown tables + prose on GitHub, CSV field definitions

Scraping: GitHub raw markdown from google/transit repo. Structured table parsing.

Not started
Needed: 00b_parse_gtfs_spec.py
Gap: Constraints are embedded in table cells and field definitions, not natural language paragraphs. Needs dedicated table parser.

GPT-4 Synthetic Augmentation

LLM-generated constraint paraphrases and edge cases. Used to augment training data by creating variants of real constraints with different wording, domains, and threshold values. Also generates adversarial examples.

Sources: Paraphrases of existing annotated constraints, cross-domain transfer examples, edge case generation

Format: Generated JSONL with same schema as real annotations

Approach: Few-shot prompting with real examples, constrained generation to maintain IR-compatible output.

Not started
Needed: 03b_synthetic_augment.py
Gap: 03_auto_annotate.py labels candidates but doesn't generate new synthetic constraints from scratch.
